What actually happens, five ways

Every code path in the fitness-studio chatbot, from pod boot to a cross-service membership lookup. Companion to the root README's architecture overview — this is the step-by-step.

Workflow 1

App startup

app.main.lifespan — runs once per pod, before any request is served. A read-only freshness check, not ingestion.

01
Pod starts → lifespan() begins
02
check_faq_freshness() Loads the FAQ markdown (Drive export in prod, data/faq.md local) and hashes it.
03
Hash already in pgvector?
yes — log "in sync", nothing written no — log "stale, run the offline ingest job" (workflow 1b)
04
Build the model + assistant set One shared ChatOpenAI; one Assistant per Route — MEMBERSHIP_REGISTRATION, SUPPORT, GENERAL (chat model + FAQ tools), SUMMARIZE (summarize model, no tools).
05
Router + SessionStore constructed, attached to request.state
06
Pod ready to serve traffic
Why read-only: keeping embedding compute (and its Drive-read dependency) out of the request-serving pod's startup critical path. chat_model(), router_chat_model(), summarize_model(), vector_store(), embedding_model() are all @lru_cached in app/ai_config.py — built once, reused by every request.

Workflow 1b

Offline FAQ ingestion

scripts/ingest_faq.py — runs as a Kubernetes Job (off by default), not from the app pod.

01
Job starts → load_faq_knowledge() → _load_markdown_text()
02
FAQ content hash already ingested?
yes — no-op, log and skip, job completes no — continue to re-ingest
03
_delete_stale(SOURCE_ID) Deletes every old chunk for this source — idempotency is whole-document, not per-chunk.
04
MarkdownHeaderTextSplitter Splits the FAQ by # / ## headers.
05
vector_store().add_documents(chunks) → job completes

Any FAQ edit re-ingests everything for that source, not just the changed section — the hash is whole-document. Triggered manually today (helm upgrade ... --set ingestJob.enabled=true); a scheduled CronJob or a Drive-webhook trigger are the natural next steps.

Workflow 2

POST /chat

The main request path — every step below runs synchronously per request.

01
is_flagged(message)? — OpenAI Moderation API
flagged — log, raise HTTPException(400), stop here clear — continue
02
Resolve session_id — from the request, or a fresh uuid4()
Router.route() — app/router.py
Message empty?
yes → Route.GENERAL
Keyword short-circuit match?
join / register / membership / waitlist / etc → MEMBERSHIP_REGISTRATION summarize / tldr / resolved / etc → SUMMARIZE no match → LLM classifier, temperature 0
Parse the label → MEMBERSHIP_REGISTRATION / SUPPORT / SUMMARIZE / GENERAL. Unparseable → GENERAL.
Assistant.chat() — app/assistant.py
route == SUMMARIZE?
yes → summarize sessions.transcript(session_id), no tools bound no → assistants[route].chat(message)
model.invoke(messages) → response has tool_calls?
no → return response content yes → execute each tool call, append ToolMessages, loop
iteration < MAX_TOOL_ITERATIONS (4)?
yes → back to model.invoke() no → return the last message's content
03
sessions.append_turn(session_id, message, reply)
04
log.info(session_id, route, message, reply) — one line per turn
05
Return ChatResponse {agent, reply, session_id}
  • Moderation runs before session resolution and routing — a flagged message never reaches the session store, router, or any model call.
  • SUMMARIZE is the only route that ignores the literal incoming message — the trigger word itself ("resolved", "tldr") carries no content worth summarizing.
  • The tool loop is bounded by iteration count, not a retry mechanism — transient .invoke() failures are a separate, still-open gap (see README's Next Steps).

Workflow 3

GET /internal/faq/search

The non-agentic path — no LLM, no router, no session involvement.

01
GET /internal/faq/search?q=...&topK=... → search_faq_raw(q, topK)
02
k = clamp(topK, 1..MAX_TOP_K), or DEFAULT_TOP_K if unset
03
vector_store().similarity_search(q, k)
04
Map hits to {section, source, text} → return list[FaqSnippet]
  • search_faq_raw() is the same function the search_studio_faq tool calls from inside workflow 2's assistant loop — this endpoint exists to inspect retrieval quality directly (used by evals/test_ragas_faq.py's context-precision checks too).
  • No auth today — see README's Keycloak-based JWT authentication Next Step.

Workflow 4

Membership status lookup

The lookup_membership_status tool call — made from inside workflow 2's assistant loop, only for the MEMBERSHIP_REGISTRATION route. Crosses into two sibling Spring Boot services outside this repo.

studio-chatbot · the tool call
Assistant decides to call the tool Only reachable from the MEMBERSHIP_REGISTRATION route, mid tool-loop.
Exactly one of email / phone?
neither or both → refuse, ask again exactly one → proceed
GET membership:8082/api/memberships/lookup The only cross-service call this repo ever makes.
Format the response One line per membership + schedule, or a plain-language miss/error — handed back to the model as a ToolMessage.
membership service · resolving the identifier
Email given?
yes → that's the resolved email no, phone given → ask ContactsClient
ContactsClient calls contacts:8081/api/contacts Fetches the full list, filters by phone client-side — that service has no phone-search endpoint of its own.
Resolved email is null?
yes → 200, empty list no → query memberships by email
findByEmailIgnoreCase Returns 200 with the matching membership(s), possibly still empty.
membership never queries contacts by name — only by the phone it was just handed

Narrows the gap, doesn't close it. Neither service checks that the caller is the email or phone they typed — it only stops "search anyone by name." "Check on my friend John" still gets refused until John's own identifier is supplied — see app/agents/membership.py's system prompt.

Malformed request
"Provide exactly one of email or phone, not both or neither."
Unknown / no membership
"No membership found for <identifier>." — same response either way; the tool can't tell the two apart.
Service unreachable
"Membership lookup is temporarily unavailable — please try again shortly."
